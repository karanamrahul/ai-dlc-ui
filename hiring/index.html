The robot analogy

A Wi-Fi stack is a robot: a planner, middleware, a motor driver, a bus and a controller.

Each robot part on the left maps to the Wi-Fi part on the right.

  • RobotWi-Fi
  • Mission planner decides what to do↔hostapd start AP, add links, rekey
  • Middleware turns plans into commands↔nl80211 → cfg80211 → mac80211
  • Motor driver on the main computer↔Host driver ath10k / ath11k / ath12k
  • Bus messages to the controller↔WMI commands and HTT messages
  • Motor controller firmware↔WLAN FW
  • Hardware fast path skips the main computer↔NSS + NSS FW offload
  • Parts bin and conveyor tickets↔SKBs and the SKB recycler pool
  • Controller fault, watchdog restart↔FW crash and recovery
  • Main computer crash, black box↔APSS crash, pstore and ramdump
  • Hardware-in-the-loop rig↔Two Alder boards: DUT + peer
  • Regression vs the last good build↔Baseline vs candidate, judged by gates

The two-board setup

One board runs the image under test, the other plays the clients.

1 · Static, no board

From the patch, compute what it touches: callers, the WMI/HTT hop to the other side, the layers. Then find twin functions in other drivers and components where the same bug may live.

2 · Dynamic, on the boards

Run only the scenarios the patch touches, on the baseline build and then the patched build, and let the gates compare them.

Per patch

  1. Patch
  2. Static impact patch_impact.py, ~7 s per commit
  3. Scenarios selected
  4. Run on baseline
  5. Run on candidate
  6. Compare
  7. Gates
  8. PASS / WARN / FAIL report exit code 2 on FAIL, works as a CI step

Honest coverage

The Alder boards are assumed to carry ath12k-class radios (assumption, to verify). ath10k and ath11k get static analysis and twin checks only, unless boards with those radios are added.

ath12k only

MLO: multi-link peers

An MLD AP adds and removes links; each link gets its own peer and vdev in the driver and the FW.

Like a robot: two grippers told to let go at once; their acks race back and the controller frees the wrong one.

Where it breaks

  • Per-link peer deletes sent together race on the delete response.
  • Crash on link removal.

REAL, upstream Linux, static

Static check

Commit 01cc0f59aac (2026-06-29) “wifi: ath12k: fix MLO peer delete race”.

  • Changed: ath12k_peer_delete, ath12k_peer_create, ath12k_peer_mlo_link_peers_delete, ath12k_peer_delete_resp_event, ath12k_wait_for_peer_delete_done
  • 21 callers
  • Selected: peer_churn, mlo_link_churn, slo_basic, fw_crash_recovery
  • ath10k/ath11k twins, by hand: not affected. ath11k sends one delete and waits before the next; the race needs simultaneous multi-link deletes.

Board test: mlo_link_churn

20 loops of link remove/add with traffic.

  • Signals: dmesg, ramdump, peers, 1-link vs 2-link throughput, slab

Peer lifecycle

A station associates, the driver and FW create and map its peer, and on disassociation both sides tear it down.

Like a robot: a tool is checked out and handed back, but the tool log never strikes it off.

Where it breaks

  • Peer or station memory leaked
  • Use after free
  • Stale peer after FW restart

SKB ownership in the data path

Who owns each buffer as it crosses from mac80211 to the rings, the FW and back.

Like a robot: every parcel on the conveyor carries one owner’s ticket; lose the ticket and the parcel sits there forever.

Where it breaks

An skb leaked or double-freed on an error path, or when a peer is torn down mid-traffic.

REAL, upstream Linux, static

Static check

Commit 7393878255e (2026-06-23) “wifi: ath10k: fix skb leak on incomplete msdu during rx pop”.

  • Changed: ath10k_htt_rx_pop_paddr32_list / paddr64_list
  • No twin in ath11k/ath12k: the path exists only in ath10k. Sibling amsdu_pop already frees correctly.

Board test: skb_ownership_traffic

15 loops tearing the peer down during traffic.

  • Gates: slab_slope, kmemleak, peer_leak
QSDK only, not in upstream Linux

SKB recycler

Freed buffers go to a per-CPU pool instead of slab, and the next allocation reuses them.

Like a robot: a spare-parts bin by the line; when parts go out and never come back, the line stalls.

Where it breaks

  • Buffers never returned: the pool drains
  • Buffer reused while still owned: use after free
  • Wrong-size buffer reuse

Static check

No public upstream commit exists to analyze. This scenario is board-only.

Board test: skb_recycler_stress

30 traffic bursts.

  • Pool count before, each loop, after cooldown
  • skbuff_head_cache slab slope

Paths /proc/net/skb_recycler/* are placeholders to verify.

Testbed demo

All drivers

FW crash and recovery

The WLAN FW asserts; the host dumps it, tears down and restarts, and mac80211 rebuilds vdevs and peers.

Like a robot: a motor controller faults; cut its signal lines before rewiring it, or a stray pulse hits a wire you just pulled.

Live finding · lead to review, not proven

ath12k may have the ath11k AHB recovery bug. ath12k disables interrupts only in ath12k_core_reset, queued only from mhi.c; its restart path frees DP rings with interrupts enabled, the same structure as the ath11k AHB bug.

Unknown: whether an ath12k AHB crash reaches restart without reset.

Where it breaks

  • Interrupts firing while rings are freed
  • Peers or memory leaked across restart
  • Service not restored

REAL, upstream Linux, static

Static check

Commit f7a74e131d3 (2026-07-27) “wifi: ath11k: disable interrupts during firmware crash recovery”.

  • 42 callees, incl. dp_pdev_free, hal_srng_clear, ce_cleanup_pipes, wmi_detach
  • Q2 twin: ath12k/core.c ath12k_core_reconfigure_on_crash marked MISSING (fix-token coverage 0, similarity 0.44)

Board test: fw_crash_recovery

3 injected crashes via debugfs simulate_fw_crash (path to verify).

  • Recovery checks, peers, throughput restored

Testbed demo

Glossary

The words on this page, in one line each.

Messages

  • WMI: control commands and events between host driver and WLAN FW
  • HTT: data-path messages, such as peer map and RX indications
  • QMI: the channel FW uses to say it is ready
  • MHI / AHB: the buses to the radio, PCIe-style and on-chip

Wi-Fi

  • vdev: a virtual interface in FW, such as one AP
  • peer: one connected station, tracked by driver and FW
  • MLO / MLD: multi-link operation; one device on several links
  • SLO: single-link operation
  • GTK: the group key, rolled during rekey
  • EAPOL: the key-handshake frames

Memory

  • SKB: a Linux network buffer
  • SKB recycler: QSDK per-CPU pool that reuses SKBs
  • slab: the kernel allocator; its growth per loop is the slab slope
  • kmemleak: kernel tool that reports unreferenced objects
  • UAF: use after free

Platform and test

  • NSS: the network offload engine and its FW
  • APSS: the application processor running Linux
  • DUT: device under test, Board 1
  • HIL: hardware in the loop, the two-board rig
  • Twin: a similar function in another driver that may share the bug
  • Gate: a rule comparing candidate to baseline

Static results are REAL on upstream Linux; testbed results are SIMULATED. Nothing has run on the Alder boards yet.
